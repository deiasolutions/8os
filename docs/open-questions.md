## Surfaced during Block 2 implementation

### OPEN-Q-005: When does the `_ops` scope materialize?
**Surfaced:** 2026-04-26 in `kernel.ir.new` for tier 2 records
**Spec gap:** Block 1 §1.1 shows `ir/_ops/_scope.yml` in the on-disk tree, but §7.6.1 (`kernel.init`) only requires init to write `ir/<scope>/_scope.yml` for the *user* scope. The kernel needs an `_ops` scope to anchor tier 2 records but the spec doesn't say who creates it.
**Best-guess implementation:** init creates only the user scope. The `_ops` scope (and the three category subdirectories `resolver-selection/`, `authorization/`, `capability-update/`) materialize lazily on the first tier 2 write, via `ir_ops._ensure_ops_scope`.
**Resolution needed by:** when kernel-authored tier 2 records become a hot path; lazy materialization is fine for v0.1.

### OPEN-Q-006-RESOLVED: Where does the outside-contact code for `kernel.bridge.cross` live?
**Surfaced:** 2026-04-26 in `kernel.bridge.cross` implementation
**Spec gap:** Block 1 §7.6.11 specifies the wire shape (input, output, error codes, atomicity rules) but doesn't say whether the kernel binary makes outbound network calls or whether outbound transport is the caller's responsibility.
**Best-guess implementation:** v0.1 `bridge.cross` is the *recording* side of the boundary only — it validates the bridge and authorization, writes a tier 3 event recording the crossing, and echoes the caller's payload back as the response. Real network/HTTP semantics are deferred to a future block ("Block 3" — bridge implementations).
**Resolution (Block 3 Piece 3, 2026-04-27):** Bridge code lives in `src/eightos/bridges/<bridge>.py`, registered via the bridge (I, R)'s `implementation:` frontmatter field (`<module>:<function>`). `kernel.bridge.cross` reads that field at dispatch time, imports the function, and calls it with `(bridge_id, payload, authorization, repo)`. The function returns `{resolution, cost_actual, audit}`; `bridge.cross` records the real cost and resolution in the tier 3 event. Bridges WITHOUT `implementation:` keep the v0.2 echo behavior (backward-compatible — the `kernel.self` cogito bridge takes this path unchanged). The first real bridge is `anthropic` (Anthropic Messages API) at `src/eightos/bridges/anthropic.py`. Reference: Block 3 Piece 3 commit body, `ir/_kernel/bridge/anthropic.md`.

### OPEN-Q-007: ID format and global uniqueness
**Surfaced:** 2026-04-26 in `kernel.ir.new`
**Spec gap:** Block 1 §Conventions says "IDs are stable, human-readable slugs assigned at creation, never reused, never silently mutated", but doesn't say whether IDs are globally unique within a repo or scoped (e.g. `<scope>/<slug>`).
**Best-guess implementation:** ID = slug verbatim, must be globally unique across the repo. Collisions raise `ALREADY_EXISTS`. References (`depends_on`, `parent_id`, etc.) are bare slugs resolved via `id-to-path`.
**Resolution needed by:** when slug collisions become a real ergonomics problem (likely never if scope-prefixed naming conventions emerge organically).

### OPEN-Q-008-RESOLVED: Resolver_id on operation events
**Surfaced:** 2026-04-26 in tier 3 event writing
**Spec gap:** Block 1 §5 lists `resolver_id` as a required field on every event. But operation events authored by the kernel itself (init, ir.new, ir.expand, etc.) have no semantically meaningful resolver — the kernel performed the bookkeeping.
**v0.1 best-guess (now superseded):** Operation events use the literal string `"kernel"` as `resolver_id`.
**Resolution (Block 2.7, 2026-04-27):** Use `kernel.binary@<__version__>` (e.g., `kernel.binary@0.1.0`) for kernel-self-observed records — the bootstrap (I, R), the `_kernel`-scope foundational records, and tier 3 events authored through the `kernel.self` cogito bridge. The version suffix makes the kernel's self-observations specifically attributable: future audits can distinguish records produced by v0.1 vs v0.2 vs v1.0 kernels without joining against a separate version table. The `authored_via` field carries the bridge (`kernel.self`); `resolver` carries the binary id. Two semantically distinct fields, no longer collapsed onto the same string. Implemented as `KERNEL_BINARY_RESOLVER_ID = f"kernel.binary@{__version__}"` in `src/eightos/__init__.py`. Reference: BLOCK-2.7-SPEC-CORRECTIONS Question 1 (cogito mechanics) and the discipline established by Patch 5 (resolver vs bridge are different categories; collapsing them is an implementation drift, not a spec decision).

## Surfaced during Block 2.5 (first projection workload)

### OPEN-Q-010-RESOLVED: `kernel.ir.new` does not honor Block 1 §2's "PROJECTION-SPECIFIC EXTENSIONS" clause
**Surfaced:** 2026-04-26 porting a PRISM-IR v1.1 Level 1 example
**Spec gap:** Block 1 §2 explicitly reserves the ability for projection types to declare additional required frontmatter fields (the example given is `authorizes` for the authorization projection). PRISM-IR v1.1 Level 1 relies on this clause: it requires `prism`, `version`, and `conformance` as additional frontmatter keys on top of the canonical 8OS frontmatter. But `kernel.ir.new` accepts only the fixed input set (its JSON Schema marks `additionalProperties: false`), and its writer hard-codes the 8OS-only frontmatter shape. There is no way through the SDK to add projection-specific frontmatter fields at creation time.
**Best-guess implementation:** Block 2.5 created the PRISM-IR (I, R) with 8OS-only frontmatter and embedded the `prism` / `version` / `conformance` declarations inside the body's YAML fenced block (which is also where the v1.0.0 PRISM-IR top-level body schema lives). The 8OS `id` and the PRISM-IR body `id` match per v1.1 identity discipline. This composes — the round-trip works, the file is valid PRISM-IR Level 1 by the spec's content requirements — but the canonical Level 1 frontmatter shape from v1.1 §"8OS-Compatible Frontmatter" is not reproducible through `kernel.ir.new`.
**Resolution needed by:** before Level 1 PRISM-IR runtimes start consuming 8OS-hosted .prism.md files, since they will look for `prism` / `version` / `conformance` in frontmatter, not body. Two-sided fix: (a) `kernel.ir.new` accepts an `extensions` map and writes it through; the input schema permits extra keys when `projection_types` declares a projection that owns them; (b) PRISM-IR v1.2 amends Level 1 to allow body-side declaration as equivalent to frontmatter declaration. (a) is cleaner and keeps v1.1 stable.
**Resolution (Block 2.7, 2026-04-27):** Resolved per option (a). Spec §2.1 specifies projection-declared frontmatter extensions; `kernel.ir.new` accepts a `frontmatter_extensions` map; the kernel reads each projection's body for required/optional field declarations and validates the input against them. Field-name collisions with base 8OS frontmatter are forbidden. PRISM-IR v1.1 unchanged; future PRISM-IR records can carry `prism` / `version` / `conformance` as proper frontmatter extensions when the prism-ir projection definition declares them.

### OPEN-Q-011-RESOLVED: There is no `kernel.projection.add` operation
**Surfaced:** 2026-04-26 declaring the prism-ir projection type
**Spec gap:** Block 1 §1.1 places project-declared projections at `.8os/projections/<type>.yml` and §7.6 enumerates eighteen v1 operations. None of them creates a projection. The kernel-shipped projections (tier3-event, authorization, resolver-selection, capability-update) are written by `kernel.init` directly. There is no SDK path for a project to declare a new projection type.
**Best-guess implementation:** Block 2.5 wrote `.8os/projections/prism-ir.yml` directly with the Write tool, since the SDK provides no operation. This is the only direct-file-write Block 2.5 performed; everything else went through `8os <op>`. The reindex check still passes because projection files don't participate in the input-set hash (projection-to-ids is built from (I, R) frontmatter, not from projection declarations).
**Resolution needed by:** before projections become a routine extension point. A `kernel.projection.add` op (v1 or v1.1) accepting the projection YAML schema fields, validating them, and writing atomically would close this gap and make the projection extension surface symmetric with bridges and resolvers.
**Resolution (Block 2.7, 2026-04-27):** Resolved differently than the original best-guess — there is no typed `kernel.projection.add` op in v0.2. Instead, "kernel-configuration is content": projection definitions are (I, R) records of `projection_types: [_kernel.projection]` authored through `kernel.ir.new`. Same pattern for resolvers, bridges, scopes, surrogate-lineage records. v0.2 trims v0.1's eighteen ops to sixteen by removing `kernel.resolver.add` and `kernel.bridge.add`. The SDK is now uniform with respect to configuration vs. content: everything goes through ir.new.

### OPEN-Q-012-RESOLVED: Slug-as-ID forces a choice between identity and file extension convention
**Surfaced:** 2026-04-26 picking a slug for the PRISM-IR example
**Spec gap:** Block 1 derives the on-disk filename from the slug (`ir/<scope>/<slug>.md`) and OPEN-Q-007 froze "ID = slug verbatim". PRISM-IR v1.1 specifies the file extension `.prism.md`. To get the right extension under the current implementation, the slug must end in `.prism` — which then becomes the (I, R) ID, e.g. `expense-approval.prism`. That ID then leaks the file-format convention into every cross-reference, dependency edge, and event log line. The alternative — a clean ID like `expense-approval` — produces `ir/<scope>/expense-approval.md`, losing the PRISM-IR extension convention.
**Best-guess implementation:** Block 2.5 chose slug = `expense-approval.prism` to honor PRISM-IR's `.prism.md` extension. The cost is an ugly ID. The fix is to decouple ID from filename: let projections declare a filename-suffix convention (`.prism.md`) that the kernel applies during write, with the ID staying clean. This pairs naturally with the OPEN-Q-010 fix — projections become a real, kernel-aware extension surface rather than an opaque label.
**Resolution (Block 2.7, 2026-04-27):** Spec §2.2 specifies the filename-suffix mechanism: projection definitions declare `filename_suffix` in their body; `kernel.ir.new` applies the suffix at write time; ID stays clean. The migration script translates Block 2.5's ad hoc `file_extension` field name to the standardized `filename_suffix`. After migration, the example record is accessible at id `expense-approval` while its filename retains `.prism.md`. OPEN-Q-010 and OPEN-Q-011 also resolve through the same mechanism (kernel.ir.new accepts frontmatter_extensions; project-declared projections are (I, R)s authored through ir.new).

### OPEN-Q-020-RESOLVED: `kernel.init` was not idempotent; v1.0 §7.2 unimplementable
**Surfaced:** 2026-04-27 in Block 2.9 finding zero (before Piece 1 authoring).
**Spec gap:** v1.0 §7.2 promised: *"Implementations that need to fold the new vendored content into a running v0.2 repo can do so by re-running `8os init` against the existing repo (which is already idempotent per v0.2 §7.2's discipline) or by running `8os reindex` after upgrading the binary."* Neither path worked. `init_op.py:run` raised `ALREADY_EXISTS` whenever `.8os/version` existed; `reindex_op.py:run` only regenerated indexes from existing inputs and did not write vendored bodies, projection-definition (I, R)s, or new resolver (I, R)s. The v0.2 → v1.0 upgrade path described in the spec did not exist in code. Block 2.8 closed without exercising it.
**Resolution (Block 2.9, 2026-04-27):** Implemented `kernel.init` upgrade-mode. When `.8os/version` exists, the op compares against the kernel binary's `__version__`. Equal → noop, no event, no work. Binary newer → upgrade — fold in net-new vendored content with skip-if-exists semantics; preserve sealed bodies; preserve all (I, R)s, bridges, and user content; emit one tier 3 event in `_ops` authored through `kernel.self`; last write is `.8os/version` (idempotency anchor). Existing newer than binary → `KERNEL_VERSION_MISMATCH` (refuse in-place downgrade). Kernel binary version bumped 0.1.0 → 1.0.0 to reflect Block 1 v1.0 representation alignment; `KERNEL_BINARY_RESOLVER_ID` is now `kernel.binary@1.0.0` on new records (v0.2-era records keep `@0.1.0`, exactly the audit-trail discipline the suffix was designed for per OPEN-Q-008-RESOLVED).
**Implementation:** `src/eightos/sdk/init_op.py` (run dispatcher + `_run_noop` + `_run_upgrade` + helpers); `kernel.init.v1.output.json` schema extended with optional `mode`, `previous_version`, `kernel_version`, `added.{vendored_projection_bodies,projection_definitions,kernel_internal_resolvers}` fields and nullable `event_id`; tests in `tests/test_init.py` covering idempotency at matching version, v0.2 → v1.0 upgrade with idempotent re-run, single-event-in-_ops with kernel.self provenance, and downgrade rejection. v1.0 §7.2 spec text stays correct as written; the implementation now matches it. **NOT a v1.0.1 fold-back amendment — this is implementation matching spec, not spec changing.** Reference: Block 2.9 commits `e85e49b` (Task 0a code), `42cf4f7` (Task 0b state), and `554d62a` (Task 0a follow-up: body refresh).

All these changes mean existing vendored bodies need to update across binary versions — the seal is against USER edits, not against binary upgrades. v0.2 §1.3 and v1.0 §1.2 don't make this explicit. The Block 2.9 Task 0a implementation now refreshes changed bodies via the upgrade-mode mechanism, but the spec is silent on the discipline.
**Best-guess implementation (Block 2.9 implements correct behavior):** `init_op.py:_run_upgrade` compares each body's content against the binary's current declarations; rewrites if different (`refreshed`); leaves alone if same. Sealed against user edits; updated on binary upgrade. The Block 2.9 spec amendments file or v1.0.1 housekeeping should clarify v0.2 §1.3 and v1.0 §1.2 to say "sealed against user edits; binary owns and refreshes them across binary versions".
**Resolution (v1.0.1-partial Amendment 3, 2026-04-27):** Vendored projection bodies are sealed for the lifetime of a single kernel version, not absolute. Bodies refresh during `kernel.init` upgrade-mode when the binary's version is newer than `.8os/version`. Records authored against prior bodies remain valid as long as the new bodies are additive-compatible. The kernel binary is the unit of body authority across versions: two binaries with the same version string MUST ship identical vendored bodies. v1.0.1-partial bumps `__version__` accordingly; future development binaries that diverge from a released version must declare a different version string (e.g., `1.0.2-dev.1`). Reference: `docs/spec/8OS-BLOCK-1-SPEC-v1.0.1-PARTIAL.md` Amendment 3, `docs/v1.0.1-partial-report.md` Piece 3.

### OPEN-Q-029: PRISM-IR node id namespacing in kernel id-to-path
**Surfaced:** 2026-04-28 in Block 3 Piece 5 (the SCAN dogfood end-to-end run).
**Spec gap:** PRISM-IR `nodes:` carry `id:` fields that name each node within the doc. ### OPEN-Q-030: Workload-meta-properties not surfaced in resolution_text drift round-trip

### OPEN-Q-025: Calibration corpus predicted_value/actual_value type heterogeneity
**Surfaced:** 2026-04-27 in Block 2.9 Piece 4 (visible in `.8os/index/calibration-corpus.yml` after cycles 1-3).
**Spec gap:** Predictions store `predicted_resolution: <free-form>` (per v1.0 §3.1 — "Shape varies by intention type: boolean for yes/no questions, numeric for continuous outcomes, structured object for richer predictions"). Resolutions are authored via `kernel.ir.resolve` which writes `resolution_text: <string>`. The calibration-corpus index reconstructs `actual_value` from the subject intention's `resolution_text` (per `_compute_calibration_corpus` in `_indexes.py`). Result: predictions store `predicted_value: <typed value>` (bool, number, dict) but actuals store `actual_value: <full resolution text>`. Future calibrators comparing predicted vs actual need parsing logic to extract a comparable shape from `actual_value`'s prose.
**Best-guess implementation (Block 2.9 lives with mismatch):** Block 2.9's predictions are `predicted_value: True`; actuals are `'pytest exit code 0. PASS. Elapsed 24293ms. Tail: ...'`. A future calibrator computing accuracy needs to parse the resolution text to extract the boolean answer. This is fine for n=3 but doesn't generalize.
**Resolution needed:** Either:
1. `kernel.ir.resolve` extended to accept structured `resolution: {value: <typed>, text: <string>, ...}` payloads (parallels how predictions work) — moves resolution-shape declaration into the op interface.
2. Each domain's calibration policy declares a `parse_actual` hint (function reference or regex) the calibrator uses — moves parsing into the policy.
3. Corpus index stores both raw and parsed forms — defers comparison logic to the calibrator's choice.
Likely v1.x evolution; not blocking v1.0.1 fold-back. Severity: medium — calibrator implementations will need to choose; the spec gap is real but not urgent.
**Empirical evidence (Block 3 Piece 5, SCAN dogfood):** every node in the SCAN flow JSON-encodes its structured output into `resolution_text` so the next node can `json.loads` it. fetch-sources writes `{items: [...]}`; score-relevance writes `{items: [{...with score...}]}`; filter-and-rank writes `{items: [...top-N...], top_n: 5}`; generate-briefing writes raw markdown. Four nodes, three different JSON shapes plus one prose. The pattern works, but it pushes typing discipline onto every adapter individually and bloats `resolution_text` (a 2KB JSON dump as the "resolution" is awkward). **The empirical signal favors option 1** — extending `kernel.ir.resolve` to accept a structured payload alongside the text resolution would let resolvers declare their output shape once, in their own (I, R), rather than ad-hoc per call.
**Status:** explicitly deferred at v1.0.1-partial; sharpened in Block 3 Piece 5 with empirical evidence favoring option 1. Affects future calibrators AND the Shape 4 adapter pattern. Reference: `docs/spec/8OS-BLOCK-1-SPEC-v1.0.1-PARTIAL.md` Deferred section; Block 3 Piece 5 commit body.

### OPEN-Q-036-RESOLVED: Policy-evaluation cache write path under axiom 8
**Surfaced:** 2026-05-02 in `BLOCK-5.0-PHASE-A-PRIME-REPORT` § OPEN-Q-A4 (paralleling OPEN-Q-N1's bootstrap concern; not numbered in the original amendment proposal).
**Spec gap:** Whether the `_kernel.policy-evaluation` cache writes (Block 1 §8.6, authored during the kernel's policy-evaluation phase) go through `kernel.ir.new`'s validation pipeline. Like bootstrap, the cache writes face a structural recursion concern: invoking the policy-evaluation phase while authoring a policy-evaluation record produces an unbounded loop.
**Block 5.0 Phase A′ resolution (principled bypass):** Policy-evaluation records are authored via `op_pipeline._author_policy_evaluation` (`src/eightos/op_pipeline.py:535`), which the function's own docstring names: *"Bypasses `kernel.ir.new` to avoid recursive policy-phase invocation."* The bypass uses the same atomic-commit + event-emission + index-regeneration discipline as `kernel.ir.new` and writes records satisfying the same (I, R) shape contract; it skips only the policy-evaluation phase that would otherwise loop. Kernel spec v0.2 names policy-evaluation cache as the second of two structural carve-outs in §"Axiom 8 — Reflexivity".
**Status:** resolved by Block 5.0; principled-bypass classification recorded in kernel spec v0.2 and `BLOCK-5.0-PHASE-A-PRIME-REPORT`.
