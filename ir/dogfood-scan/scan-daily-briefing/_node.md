# Intention

Run the SCAN-pillar daily briefing flow described in the PRISM-IR
document below. A registered PRISM-IR decomposer should manifest the
flow as a kernel-hosted (I, R) graph; the factory should walk that
graph to completion and produce a daily briefing artifact.

The PRISM-IR document itself is the substantive content — everything
above this line is 8OS frontmatter. Everything below is a Level 0
PRISM-IR doc (v1.1.0) that describes the SCAN flow's process shape.
The decomposer's prompt knows how to read this exact format.

```yaml
v: 1.1
id: scan-daily-briefing
name: SCAN-pillar daily briefing (Wave 1)
domain: information-curation

intention: |
  Each morning, fetch top items from selected sources, judge their
  relevance to a stated briefing topic, pick the top items by
  relevance, and compose a structured briefing artifact summarizing
  what's worth reading today.

failure_tolerance: graceful-degradation
constraints:
  - sla: 5min
  - fail: log-and-continue

params:
  briefing_topic: AI infrastructure and governance, week of 2026-04-27
  top_n: 5
  fetch_window_hours: 24

nodes:
  - id: start
    t: start

  - id: scan-fetch-sources
    t: task
    name: Fetch source items
    description: |
      Pull recent items from declared sources (HackerNews top stories
      and arXiv recent submissions in cs.AI / cs.LG). Return a list of
      items each with title, url, abstract (when present), and source
      label.
    o: { op: script, resolver: fetch-sources }

  - id: scan-score-relevance
    t: task
    name: Score per-item relevance
    description: |
      For each fetched item, judge how relevant it is to the briefing
      topic. Output a relevance score in [0, 1] per item plus a brief
      reason. The scorer reads the items list, the briefing topic, and
      the desired top_n.
    o: { op: llm, resolver: score-relevance }

  - id: scan-filter-and-rank
    t: task
    name: Pick top-N by score
    description: |
      Select the top_n items by score, breaking ties by source priority
      (HN > arXiv as a default). Return the ranked list.
    o: { op: script, resolver: filter-and-rank }

  - id: scan-generate-briefing
    t: task
    name: Compose the briefing
    description: |
      Compose a markdown briefing artifact summarizing the top items
      with a short paragraph each. Open with a one-paragraph framing
      that ties the items to the briefing topic. Close with a list of
      raw links for follow-up.
    o: { op: llm, resolver: generate-briefing }

  - id: end
    t: end

edges:
  - { s: start, t: scan-fetch-sources }
  - { s: scan-fetch-sources, t: scan-score-relevance }
  - { s: scan-score-relevance, t: scan-filter-and-rank }
  - { s: scan-filter-and-rank, t: scan-generate-briefing }
  - { s: scan-generate-briefing, t: end }
```

## Why this shape

The shape mixes inside resolvers (fetch-sources, filter-and-rank) and
bridge-crossing LLM resolvers (score-relevance, generate-briefing) so
the dogfood exercises both dispatch paths. Two bridge crossings at
non-zero coin cost exercises OPEN-Q-024 territory for the first time.
Structured payloads pass between every node (item lists, score-
annotated lists, ranked lists, briefing markdown) so the Shape 4
adapter pattern is exercised across heterogeneous shapes — that
sharpens OPEN-Q-025.

## Why this scope

This (I, R) lives under `dogfood-scan` rather than the user scope.
SCAN is its own pillar of the broader 8OS product; mixing the dogfood
graph with the user-scope kernel-development records would muddle
provenance. A dedicated scope makes the "this was generated by the
factory from PRISM-IR" provenance visible at a glance.

## What happens when the factory dispatches this

1. Walker finds this leaf (status=open, no deps, no expanded_into).
2. Selector matches `domain: prism-ir-decomposition` to the
   `prism-ir-decomposer` resolver's capability declaration.
3. Dispatcher routes through the Anthropic bridge with the decomposer's
   prompt as system message and the body above as user message.
4. Decomposer returns a JSON graph spec with four nodes (start/end
   dropped per the prompt's rules).
5. Tick's `produces == graph` branch invokes the materializer; the
   four children are authored under this expanded parent.
6. Walker's `expanded_into is None` filter ensures this leaf is not
   re-dispatched on subsequent ticks.
7. Subsequent ticks dispatch each child in topological order. Each
   child's `domain` field matches its corresponding resolver's
   capability declaration; selector picks each uniquely.
8. The terminal `generate-briefing` resolution_text IS the briefing
   artifact.

Piece 6's recomposer will eventually compose the four children's
resolutions into a recomposed parent resolution; for now this parent
stays "open + expanded" with all children resolved.
